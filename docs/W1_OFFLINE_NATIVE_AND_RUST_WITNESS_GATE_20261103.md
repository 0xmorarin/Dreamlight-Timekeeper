## Consumer / reschedule / overwriting boundaries

**Native-statically traced** common data path: \`Client.<WaitForNextOccurrence>d__262.MoveNext\` \`0x060B4D80\` loads saved oneof \`0x060B51B0\`, converts Timestamp at \`0x060B5388\`, constructs a Clock appointment at \`0x060B53F0\`, and when its await succeeds may send \`ExecuteRecurringEvent.Types.Request.RecurringEventID\` (store \`0x060B5E7C\`, RPC \`0x060B5F30\`). This **does not** establish a server's subtype Execute dispatch or successful spawn. \`Client.Clock\` appointment uses +0xF0. \`Meta.Util.Clock.Update 0x05BB4D30\` uses strict **appointment time < provider now**, whereas common recurring source readiness tests **now >= NextOccurrence**. At equality the conditions differ. Clock can be paused; its already-constructed appointment does **not** re-read the serialized NextOccurrence.

\`Profile.ActualizeRecurringEvents 0x05A2A170\` includes a bounded overdue branch; subtype GetMaxTimeInterval formulae depend on max/count and Area rather than guaranteeing a number of spawned objects. \`IRecurringEventExtensions.Reschedule 0x05AF24D0\` and each subtype's setter write +0x20. **Setter bodies do not directly emit slot62**. \`Profile.AddRecurringEvent\` has a conditional slot62 emit; Client handler \`0x0604E9B0\` can early return via \`blockRecurringEventReschedule\` +0x1D0. On profile replacement \`Client.<SetProfile>d__126\` invokes \`WaitForRecurringEvents\` (\`0x060AA13C\`), and debug-only time skip has a separate re-arm route (\`0x060915E0\`). Neither proves arbitrary offline field edit causes immediate active wait refresh or that a cold reload preserves an edited timestamp until event execution; exact order of actualization/wait/notification and CTS cancellation remains UNKNOWN.

A long-future \`2126-08-20T00:00:00Z\` is an Owner-intended suppression example, **not corruption** or a safe automatic normalization target. Setting Now is an input request, not evidence of immediate spawn. Setting a past time may trigger catch-up/next scheduling under eligibility/Area/cap conditions, not guarantee reinstatement. Existing spawned GridObjects are not removed by changing this timestamp alone.
